# ESP32 Weather Station

Локальная метеостанция на ESP32 NodeMCU-32S с BMP280 + DHT11, веб-интерфейсом в стиле Liquid Glass и переносимым LVGL UI.

## 1. Зафиксированный pinout

| Датчик | Вывод | ESP32 |
|---|---|---|
| BMP280 | VCC | 3.3V |
| BMP280 | GND | GND |
| BMP280 | SCL | GPIO22 |
| BMP280 | SDA | GPIO21 |
| BMP280 | CSB | 3.3V |
| BMP280 | SDO / SDD | GND |
| DHT11 | + | 3.3V |
| DHT11 | OUT | GPIO4 |
| DHT11 | – | GND |

При таком подключении BMP280 работает по I²C; SDO, подтянутый к GND, выбирает типичный адрес `0x76`.

## 2. Среда разработки

Рекомендуемый базовый стек:
- VS Code + PlatformIO;
- ESP32 Arduino framework;
- DeepSeek API через DeepSeek Harness;
- LVGL для локального дисплея;
- автономные статические web assets без CDN.

PlatformIO использует board id `nodemcu-32s` для NodeMCU-32S. Официальная конфигурация допускает Arduino framework и загрузку через esptool.

## 3. Секреты

Не помещайте реальный пароль Wi-Fi в Git. Для локальной работы:

```text
копировать include/secrets.example.h → include/secrets.h
внести реальные данные
```

`include/secrets.h` уже исключён из `.gitignore`.

Wi-Fi SSID проекта: `Beeline_2G_F121F9`.

Важно: строка `192.168.1.111` — фиксированный статический IPv4-адрес ESP32. Проект рассчитан на подсеть `192.168.1.0/24`, шлюз `192.168.1.1`. DHCP для ESP32 в рабочей конфигурации не используется.

Перед прошивкой проверьте, что адрес `192.168.1.111` свободен и не выдан другому устройству. Если роутер использует другую подсеть или другой адрес шлюза, эти параметры необходимо скорректировать в `include/secrets.h`.

## 4. Подготовка рабочего окружения

### Шаг 1. Установить VS Code
Установите Visual Studio Code и расширение PlatformIO IDE.

### Шаг 2. Проверить PlatformIO
Откройте терминал PlatformIO и убедитесь, что доступна команда:

```bash
pio --version
```

### Шаг 3. Открыть проект
Откройте корень `esp32-weather-station/` как workspace.

### Шаг 4. Первый build
Выполните:

```bash
pio run
```

### Шаг 5. Подключить ESP32 по USB
Проверьте COM/tty порт, затем:

```bash
pio device list
```

### Шаг 6. Загрузить

```bash
pio run -t upload
```

### Шаг 7. Смотреть Serial

```bash
pio device monitor -b 115200
```

### Шаг 8. Проверка статического IP

После прошивки в Serial Monitor должны последовательно появиться подключение к `Beeline_2G_F121F9` и строка с IP `192.168.1.111`. Если адрес не `192.168.1.111`, считать сетевой тест неуспешным.

### Шаг 9. Первый hardware smoke test
До UI и web server агент обязан убедиться в следующем порядке:

```text
BOOT → I²C scan → BMP280 → DHT11 → Wi-Fi → HTTP → LVGL
```

## 5. Настройка DeepSeek Harness

DeepSeek API совместим с OpenAI API; официальный base URL: `https://api.deepseek.com`. На текущей документации доступны `deepseek-v4-flash` и `deepseek-v4-pro`; старые имена `deepseek-chat` и `deepseek-reasoner` после 24 июля 2026 года не следует использовать для нового проекта.

Практически:
1. Создайте API key в DeepSeek.
2. Передайте key в окружение/секрет-хранилище вашего Harness, а не в репозиторий.
3. Настройте OpenAI-compatible base URL на `https://api.deepseek.com`.
4. Для рабочего coding-agent профиля используйте актуальную V4-модель, а для быстрых итераций предпочтительно более быстрый `deepseek-v4-flash`.
5. На первую команду агент обязан прочитать `.dsh/skills/**/SKILL.md`.

Не храните API key DeepSeek в `platformio.ini`, `README.md` или исходниках ESP32.

## 6. Правила вайбкодинга

Один запрос = одно небольшое изменение. После изменения агент обязан:

```text
READ → PLAN → PATCH → BUILD → TEST → REPORT
```

Для железа добавляется `FLASH`.

Перед генерацией кода агент сверяет pinout и текущую структуру. Нельзя самовольно добавлять каталоги, менять GPIO или переносить логику из одного слоя в другой.

## 7. Функциональный контракт UI

Веб-интерфейс и LVGL должны поддерживать одни и те же четыре режима:
- цифры;
- горизонтальные графики;
- столбчатая диаграмма;
- круговые шкалы.

Каждое измерение должно иметь собственную иконку и цветовую семантику. Кроме типа значения должен отображаться статус `ok/stale/error`.

UI должен быть usable на небольших дисплеях и ILI9341, без зависимости от размера браузерного viewport или конкретного разрешения TFT.

## 9. Definition of Done

Проект считается готовым, когда:
- ESP32 стабильно запускается;
- оба датчика читаются;
- ESP32 подключается к SSID `Beeline_2G_F121F9` и получает статический IP `192.168.1.111`;
- шлюз и DNS настроены на `192.168.1.1` и `1.1.1.1`;
- web UI доступен по локальному IP;
- данные обновляются в реальном времени без manual refresh;
- все четыре режима работают;
- LVGL UI переносим на ILI9341 без переписывания sensor/data layer;
- потеря Wi-Fi и ошибка датчика не приводят к зависанию устройства;
- секреты отсутствуют в Git.

## 10. Контракт API (v1, заморожен)

`GET /api/weather` → `200 application/json`, `Cache-Control: no-store`.

| Поле | Тип | Единица | Источник |
|---|---|---|---|
| `temperature_c` | number \| null | °C | BMP280 |
| `humidity_pct` | number \| null | % | DHT11 |
| `pressure_hpa` | number \| null | hPa | BMP280 (`pressure_pa / 100`) |
| `pressure_pa` | number \| null | Pa | BMP280 (`pressure_hpa * 100`) |
| `bmp280_valid` | boolean | — | успех последнего чтения BMP280 |
| `dht11_valid` | boolean | — | успех последнего чтения DHT11 |
| `bmp280_age_ms` | number \| null | мс | возраст последнего успешного чтения BMP280 |
| `dht11_age_ms` | number \| null | мс | возраст последнего успешного чтения DHT11 |
| `uptime_ms` | number | мс | `millis()` с момента загрузки |

Имена и порядок полей — часть контракта. `null` означает «значение никогда не измерялось», ошибка чтения никогда не подменяется нулём; устаревший датчик сохраняет последнее известное значение вместе с `valid=false`. Версия 2 (semantic roles / data state, например через SSE) — отдельное аддитивное решение; v1 остаётся совместимым. Версия объявлена как `kWeatherApiVersion` в `src/main.cpp` и печатается в boot-логе.

`GET /` отдаёт `web/index.html` (вшит в прошивку), `GET /health` → `200 text/plain` `OK`.

## 11. Режимы логирования и граница отображения

Логирование задаётся `-DWS_DEBUG_LOGS` в `platformio.ini`:

- `0` (NORMAL, по умолчанию) — boot/init, подключение и потеря Wi-Fi, проверка контракта, проба шлюза, старт/стоп HTTP, все `[ERROR]` и периодическая строка только при аномалии: никакого 5-секундного шума;
- `1` (DEBUG) — дополнительно все `[*][DEBUG]` строки, 5-секундные снимки Wi-Fi/HTTP и логи каждого HTTP-запроса.

Теги не меняются: `[BOOT]`, `[SENSOR]`, `[SENSOR][BMP280]`, `[SENSOR][DHT11]`, `[WIFI]`, `[WIFI][DEBUG]`, `[HTTP]`, `[HTTP][DEBUG]`, `[API]`, `[ERROR]`.

Слои и граница, за которой подключаются LVGL/ILI9341:

```text
Hardware → Sensor layer (Bmp280Reading / Dht11Reading)
         → WeatherModel (temperature / humidity / pressure + valid + age + uptime)
         → PresentationModel (semantic roles, FRESH/STALE/ERROR, диапазоны шкал)
         → WebRenderer (JSON v1 + браузер)  |  LVGLRenderer (следующие итерации)
```

Правило: рендерер читает модель, а не датчики. Словарь ролей (`temp-cold` … `pressure-high`), пороги, диапазоны шкал и окна свежести заданы в `src/main.cpp` (namespace `Roles` / `Semantics`) и в `web/index.html` (`COLOR_ROLES`, `SEMANTIC_THRESHOLDS`, `METRIC_CONFIG`, `APP_CONFIG.freshnessMaxAgeMs`); значения обязаны совпадать — соответствие «role → будущий LVGL color token» задокументировано в `src/main.cpp`.

## 12. Display is optional during development

Физического дисплея сейчас нет, и он **не требуется** ни для сборки, ни для прошивки, ни для работы станции. Display — опциональная подсистема с compile-time выбором backend'а (`-DDISPLAY_BACKEND` в `platformio.ini`).

| Конфигурация | Значение | Состояние |
|---|---|---|
| `DISPLAY_BACKEND_NONE` | `-DDISPLAY_BACKEND=0` | **текущий режим**: панели нет; headless-рендерер считает layout и draw-примитивы, ничего не рисует, но проходит self-test |
| `DISPLAY_BACKEND_ILI9341` | `-DDISPLAY_BACKEND=1` | **будущий режим**: сборка останавливается с понятным сообщением, пока не реализован backend панели |

Цепочка слоёв (каждый знает только предыдущего):

```text
WeatherModel → PresentationModel → DisplayMode → DisplayRenderer → DisplayBackend
```

- `DisplayRenderer` (`renderNumeric` / `renderHorizontal` / `renderBars` / `renderGauges`) работает только с `PresentationModel` + геометрией: не знает `Wire`, `Adafruit_BMP280`, `DHTesp`, `WiFi`, `WebServer`, не вызывает API и не пересчитывает пороги.
- `DisplayBackend` — единственное место, которое «рисует» (`drawCard` / `drawIcon` / `drawText` / `drawTrack` / `drawGauge`). Для `NONE` это no-op со счётчиком примитивов.
- Режимы (`numeric`, `horizontal`, `bars`, `gauges`) — application state (`DisplayMode` + `setDisplayMode()`), идентификаторы совпадают с Web UI.
- Иконки — абстрактные id (`temperature`, `humidity`, `pressure`, `wifi`); Web сопоставляет их со своими inline SVG, LVGL backend позже сопоставит со своим image/vector asset.
- Цвета — токены (`TEMP_COLD` … `DATA_ERROR`), RGB живёт в theme-слое (`kReferenceTheme`), значения совпадают с CSS-переменными Web.
- Геометрия — профили `320x240` / `480x320` / `800x480` / `desktop`; layout считается от размеров, в коде layout нет ни одного литерала размера панели.

### Что нужно будет сделать после покупки ILI9341

1. Определить **фактический модуль**: контроллер, интерфейс (SPI 4-wire / 8-bit parallel), наличие touch, распиновка конкретного breakout'а. Не брать GPIO из названия контроллера.
2. Выбрать свободные GPIO, не задев `GPIO21/22` (I²C, BMP280) и `GPIO4` (DHT11), с учётом boot-strapping пинов ESP32; внести их именованными константами в `namespace Pins`.
3. Добавить в `platformio.ini` `lib_deps += lvgl/lvgl` и `-DLV_CONF_SKIP=1` (или положить `lv_conf.h`), при необходимости — драйвер панели (например, TFT_eSPI/lovyanGFX) с настройкой под модуль.
4. Реализовать в `src/main.cpp` backend `DISPLAY_BACKEND_ILI9341`: `lv_init()`, `lv_display_create(w, h)`, draw-буфер, `flush_cb`, SPI + rotation + backlight; тела `DisplayBackend::draw*` заменить на обновление LVGL-объектов.
5. Переключить `-DDISPLAY_BACKEND=1`, собрать, прошить и проверить те же четыре режима на панели.
6. Модели данных, режимы, роли, токены и Web UI при этом не меняются: renderers уже получают `PresentationModel`.

**Почему LVGL пока не подключён (измерено, не предположение).** Чистый эксперимент на этой же плате (`%TEMP%`, вне проекта): LVGL 9.5 с `-DLV_CONF_SKIP=1`, урезанным набором виджетов и headless-дисплеем (без драйвера панели) даёт `liblvgl.a` = 259 533 Б `.text` + 47 514 Б `.rodata` ≈ **307 КБ flash** и ≈ **66 КБ статического RAM**. Для текущего образа (936 645 Б, 71.5 %) это ~90 % раздела приложения — свободными остаются ~130 КБ, которых должно хватить и на драйвер панели, и на шрифты. Поэтому библиотека подключается на шаге 3 выше, вместе с backend'ом, а не раньше: тогда рост памяти сопровождается реальной панелью, которую можно проверить. До этого момента проект собирается вообще без зависимости от LVGL.

Отдельно: PlatformIO ищет зависимости по тексту исходников и не вычисляет `#if`, поэтому `#include <lvgl.h>` внутри выключенной ветки всё равно включает LVGL в сборку. Именно поэтому include появляется вместе с backend'ом, а не заранее.

## 13. Web UI: режимы и история

Один dashboard, пять presentation-режимов с общими идентификаторами (`numeric`, `horizontal`, `bars`, `gauges`, `history`). Переключение вкладок меняет только presentation state: ни `fetch`, ни перезапуска polling, ни изменений API. Рендереры получают один и тот же `uiModel`, semantic roles и data states.

**History is client-side session history.** История собирается браузером из тех же ответов `GET /api/weather` (отдельного запроса и отдельного таймера нет), живёт **только в памяти текущей вкладки** и исчезает после обновления страницы. В ESP32 (RAM, NVS, LittleFS) история не хранится; backend и контракт API v1 не менялись. Persistence (IndexedDB/localStorage) — отдельная будущая итерация.

Буфер — ring buffer на типизированных массивах (время `Float64Array`, значения `Float32Array`, состояния `Uint8Array`). `null` от датчика хранится как пропуск (NaN) и рисуется разрывом линии, а не нулём; `valid=false` сохраняется как `STALE` вместе с последним известным значением.

| Период | Шаг сэмплирования | maxPoints | Точек за период |
|---|---|---|---|
| 10 с / 30 с | 1 с | 14 / 34 | 10 / 30 |
| 1 мин | 2 с | 34 | 30 |
| 5 мин | 5 с | 64 | 60 |
| 15 мин | 10 с | 94 | 90 |
| 30 мин | 15 с | 124 | 120 |
| 1 ч | 30 с | 124 | 120 |
| 3 ч | 1 мин | 184 | 180 |
| 6 ч | 2 мин | 184 | 180 |
| 12 ч | 5 мин | 148 | 144 |
| 24 ч | 5 мин | 292 | 288 |

`maxRenderPoints = 180`: даже при 288 сырых точках в SVG рисуется не более 180 (прореживание с сохранением минимума/максимума в каждом бакете, поэтому пики не теряются). Замер: 289 сырых точек → 180 нарисованных, SVG-граф < 120 узлов и не растёт с числом сэмплов.

Память worst case: 292 точки × (8 Б время + 3 × 4 Б значения + 3 × 1 Б состояния) ≈ **6.7 КБ** на вкладку; жёсткий предел `hardMaxPoints = 320` (при любом пресете). Смена периода пересобирает тот же буфер: старые точки вне нового окна отбрасываются, слишком плотный «хвост» прореживается под новый шаг — второго независимого хранилища нет.

Поведение: **refresh страницы** → история пуста, показывается empty state «Собираем историю…»; **OFFLINE** → существующие точки и график сохраняются, новые не добавляются, живой режим деградирует до `STALE`; **переключение вкладок** → ноль дополнительных запросов, polling продолжается в любом режиме.

График — собственный SVG (без Chart.js/ECharts/D3, без CDN): три полосы с **собственной шкалой Y** (влажность 0…100 %, температура и давление — динамический диапазон min/max с padding и минимальным размахом 4 единицы, чтобы 0.2 °C или 0.3 hPa не выглядели драматично), подписанные оси, интерактивный курсор (мышь/палец/клавиатура ←→, Home/End, Esc) с tooltip, а также текстовая таблица последних точек для screen reader.

## 14. PC-симулятор панельного UI (LVGL 9 + SDL2)

Панельный интерфейс разрабатывается **на Windows без физического дисплея**, и при
этом без второй реализации UI: один и тот же LVGL-код исполняется и в
симуляторе, и (в будущем) на ESP32 + ILI9341.

* Симулятор живёт в **соседнем рабочем каталоге**
  `..\esp32-weather-station-sim\` и читает общие исходники через
  `-DFIRMWARE_DIR=<этот репозиторий>`. В дереве прошивки не появилось ни
  `display/`, ни `simulator/`, ни `desktop/`, ни `drivers/`.
* Общий код (компилируется обеими целями): `include/weather_core.h` —
  дизайн-токены, семантика/пороги, 5 режимов, геометрия, layout-движок,
  `PresentationModel`; `include/lvgl_ui.h` — дерево LVGL-виджетов, тема и
  иконки; `include/lv_conf.h` — единая конфигурация LVGL (SDL включается только
  под `WS_PC_SIMULATOR`).
* Только для ПК: `sim_main.cpp` (окно, CLI, клавиатура, матрица/golden/производительность),
  `smoke_main.cpp` (минимальный smoke-тест toolchain), `demo_weather.*`
  (10 сценариев + пресеты истории 10 с…24 ч), `tools/`, `golden/`, `README.md`
  симулятора. Данные-заглушки физически не могут попасть в прошивку — они
  компилируются только в цели симулятора.
* Собираются две цели: `weather_station_simulator.exe` (настоящий UI) и
  `weather_smoke.exe` (минимальный экран: фон, стеклянная карточка, заголовок,
  значение, иконка-заглушка, кнопка). Smoke-тест проверяет рендеринг, цикл
  событий LVGL, анимации, мышь (настоящие SDL-события) и клавиатуру
  (`--self-test`, 6/6) **до** подключения погодного UI.
* Команды: `build.cmd`, `run.cmd`, `smoke.cmd`, `regression.cmd` в каталоге
  симулятора; версии toolchain, шаги INSTALL/CONFIGURE/BUILD/RUN/SCREENSHOT —
  в его README.
* В общем UI появились навигация и анимации: полоса режимов
  (`NUM/HOR/BARS/GAUGE/HIST`) создаётся из общей геометрии (`nav_button[]`),
  кликабельна мышью и доступна с клавиатуры через группу LVGL
  (`ui_attach_input_group`). На панели без touch/энкодера полоса отображается, но
  неактивна — это вопрос наличия ввода, а не UI. Анимации — только `lv_anim`
  и style transitions: переход режима 180 мс, отзыв кнопок 140 мс, tween
  значения 320 мс, ход стрелки/шкалы 420 мс; отключаются флагом `--no-animations`
  (golden-кадры снимаются с выключенными анимациями).

Проверки: матрица `3 разрешения × 5 режимов` (нет обрезки, нулевых размеров,
выхода за экран, потери подписей/иконок и неверных semantic-цветов),
golden-изображения 15 кадров с допусковым сравнением, 58 LVGL-объектов в дереве
независимо от режима и числа кадров, отчёт `--performance` (объекты, draw-буфер,
время кадра).

**Живые данные.** По умолчанию симулятор работает в режиме `LIVE`: `WinHTTP`
(нативный клиент Windows, без curl/Node/браузера/прокси и без CORS) опрашивает
`http://192.168.1.111/api/weather` примерно раз в 1.5 с в **отдельном сетевом
потоке**, проверяет HTTP-статус, валидирует JSON по контракту API v1 (те же 9
полей), собирает `WeatherModel` и передаёт снимок в UI-поток через mutex +
атомарный номер последовательности. UI никогда не блокируется на сети: при
выключенной ESP32 окно продолжает рисовать последний снимок, значения стареют до
`STALE`, бейдж показывает `LIVE OFFLINE`, а после восстановления связи данные
возобновляются. Панель статуса (`I` или `--info`) показывает источник, endpoint,
HTTP-статус, задержку, время последнего обновления, возраст данных и счётчики
опросов. API прошивки при этом не менялся — новых endpoint'ов нет. Команды:
`live.cmd probe|selftest|render|shot|demo` (подробности — в README симулятора).

> Симулятор проверяет поведение приложения/UI и рендеринг LVGL, но финальная
> проверка на железе обязательна для SPI-таймингов, цветов, ориентации,
> подсветки и поведения конкретной панели.
>
> (Simulator validates application/UI behavior and LVGL rendering, but final
> hardware validation is required for SPI timing, colors, orientation,
> backlight, and panel-specific behavior.)

## 15. Version control: Git / GitHub baseline

Проект находится под Git; upstream — GitHub-репозиторий
`vimpario/esp32-weather-station-lvgl`, основная ветка `main`.

| Что | Значение |
|---|---|
| Repository | `git@github.com:vimpario/esp32-weather-station-lvgl.git` (SSH) |
| Branch | `main` |
| Baseline tag | `baseline-2026-09-19` — точка возврата первого checkpoint |
| Secrets | `include/secrets.h` **не** в Git (в `.gitignore`); в репозитории только `include/secrets.example.h` с `CHANGE_ME` |
| Не коммитится | `.pio/`, `build/`, `cmake-build-*/`, `*.elf`, `*.bin`, `*.map`, `*.ppm`, `*.log`, `*.tmp`, `.vscode/` |
| Коммитится | `src/`, `include/` (кроме `secrets.h`), `web/`, `.dsh/skills/`, `lib/`, `platformio.ini`, `README.md`, `.gitignore`, `.gitattributes` |

`web/index.html` встраивается в прошивку побайтово
(`board_build.embed_files`), поэтому его переводы строк зафиксированы в
`.gitattributes` (`eol=lf`): иначе checkout на Windows с `core.autocrlf=true`
изменил бы встроенную страницу и её SHA-256.

### Rollback

Вернуться к состоянию checkpoint (безопасно, рабочее дерево не разрушается):

```powershell
git fetch origin --tags
git checkout baseline-2026-09-19        # detached HEAD на точке возврата
# посмотреть/собрать, затем вернуться на ветку:
git switch main
```

Откатить саму ветку `main` к checkpoint — перезаписывает историю ветки, поэтому
только осознанно и с предварительной страховкой:

```powershell
git switch -c backup/before-rollback    # страховочная ветка
git switch main
git reset --hard baseline-2026-09-19    # ВНИМАНИЕ: теряются коммиты после tag
git push --force-with-lease origin main # ТОЛЬКО с явного разрешения пользователя
```

### Правило дальнейшей разработки

Перед крупной итерацией:

```powershell
git status
git pull --ff-only
git log -1
```

После успешных тестов (билд и проверки зелёные):

```powershell
git add <relevant-files>
git commit -m "<message>"
git tag checkpoint-<YYYY-MM-DD>
git push origin main --tags
```

Не коммитить при падающем билде. Не делать `git push --force` без отдельного
разрешения пользователя. Секреты в репозиторий не добавлять.

## 16. Локализация RU/EN и golden-регрессия 320×240

**Язык — это состояние приложения, общее для Web UI и LVGL.** Единый словарь
ключей живёт в `include/i18n.h` (`Locale` = `kNone`/`kRu`/`kEn`, `TextKey`,
`tr()`), Web-страница использует те же имена ключей в своём JS-каталоге.

* ID локали — ровно `ru` и `en` (никаких `rus`/`eng`/`russian`).
* При **каждом** запуске `locale = none`, показывается экран выбора языка;
  dashboard не отображается и не опрашивает API до выбора.
* Выбор языка **не сохраняется** (нет NVS/EEPROM/localStorage) — при следующем
  запуске экран выбора появляется снова. Persistence — отдельная задача.
* Перевод только по ключам: `tr(TextKey::…, locale)`, без `if (ru) … else …` в
  местах вывода. Числа и единицы (`25.4`, `°C`, `%`, `hPa`) не переводятся,
  семантические role/state ID остаются идентификаторами.
* Ширина подписей проверяется измерением: если полная подпись не влезает в
  прямоугольник layout, берётся компактная форма из того же каталога (например,
  `Темп`/`Temp` вместо `Температура`/`Temperature`) — без уменьшения шрифта
  «на глаз» и без обрезки. На 320×240 панель использует компактные формы для
  карточек и полосы режимов.

**Шрифты с кириллицей.** Встроенные в LVGL Montserrat-шрифты содержат только
ASCII + набор FontAwesome, поэтому кириллица в них отсутствует. Общие шрифты
интерфейса генерируются из Montserrat (SIL OFL, тот же шрифт, что и встроенные)
скриптом `lib/ws_fonts/generate_fonts.py` в `lib/ws_fonts/ws_font_{14,20,28}.c`
с диапазонами ASCII + `А-я`, `Ё/ё`, `°`, тире и кавычками. Это те же ассеты для
PC-симулятора и будущего ILI9341. Оба таргета используют один и тот же
`WS_LVGL_FONTS`; без этого макроса (текущая сборка ESP32 без LVGL) файлы
компилируются в пустые единицы трансляции, поэтому прошивка не растёт от шрифтов.
Иконки-глифы (капля `LV_SYMBOL_TINT`) по-прежнему берутся из встроенного
Montserrat (только FontAwesome-подмножество), подобранного по размеру бокса.

**Golden-регрессия.** Референсный профиль — **320×240**, рендерится настоящим
LVGL SDL-симулятором (не HTML-скриншоты), сравнивается сырой логический
framebuffer до масштабирования окна. 12 кадров: экран выбора языка и пять
режимов в двух локалях (`320x240_language_ru/en`, `320x240_{numeric,horizontal,
bars,gauges,history}_{ru,en}`). Данные фиксированы DEMO-сценарием `GOLDEN`
(25.4 °C / 41 % / 1001.3 hPa + детерминированный набор истории), анимации
выключены, время не используется. Команда:

```powershell
# в каталоге симулятора
golden.cmd              # собрать, отрендерить, сравнить, вернуть код 0/1
golden.cmd update       # перегенерировать референсы (только при осознанном изменении UI)
golden.cmd tolerance 2  # допуск 2/255 на канал (по умолчанию 0 — точное сравнение)
```

Референсы лежат в Git в каталоге симулятора `golden/` (PNG), diff-изображения
пишутся во временный каталог и **не** коммитятся. Сравнение точное: 12/12 кадров
совпадают с `max_delta = 0` и `changed = 0/76800`. Дополнительно сохраняются 15
кадров `3 разрешения × 5 режимов` (`--compare-dir`) для проверки геометрии на
480×320 и 800×480.
